# オンライン版

出題者用（投影）と回答者用（スマホ）を分け、**誰が最初にボタンを押したか**の判定を Python バックエンドが行う。
正誤判定は出題者が口頭回答を聞いて ○/× ボタンで下す。

**AI を参加者として加えられる。** Jev が自動で早押しし、押したら 3 モデルの合議で回答する。
人間と同じルームで同じ問題に競う。詳細は [AI 参加者](#ai-参加者)。

同一 WiFi ネットワーク内での利用を想定している（オープンネットワークは想定外）。
ホテルや店舗の WiFi では繋がらないことがある。[繋がらないとき](#参加者のスマホから繋がらないとき)を参照。

問題データは [quiz-data.md](quiz-data.md)。
LLM 中継は出題データに依存しないため、CSV が無くてもサーバ自体は起動する。
詳細は [llm.md](llm.md)。

## 起動

```bash
npm install
npm run build -w web
cd server && uv sync && uv run uvicorn app.main:app --host 0.0.0.0 --port 8000
```

起動すると、出題者用 URL（トークン付き）と参加者用 URL が表示される。

```
  問題数: 2 問

  出題者用: http://localhost:8000/host?token=xxxxxxxxxxxx
  参加者用: http://192.168.x.x:8000/player
```

- **出題者用** URL を投影 PC で開く。参加用 QR コードが画面に出る
- **参加者**は QR を読み取り、名前を入力して参加する

`questions.csv` の検証に失敗した場合、サーバは起動するが**オンライン版は使えない**（`/host` `/player` `/ws` が 503 を返す）。
どの行が問題かを起動時に表示するので、直してから再度起動する。

サーバ自体を起動させるのは、[LLM 中継](llm.md)が出題データに依存しないため。
問題 0 件のまま出題できてしまうと、原因が分からないまま遊べない状態になるので、オンライン版の入口だけを明示的に閉じている。

> [!IMPORTANT]
> `--workers` は増やさないこと。ルームの状態はプロセス内のメモリに持つため、ワーカーが 2 つ以上あると参加者ごとに別の状態を見ることになる。

### 環境変数

| 環境変数 | 用途 |
| --- | --- |
| `QUIZ_CHAR_INTERVAL_MS` | 音声なし問題の文字送り間隔（ミリ秒/文字、既定 120） |
| `TYPESAFE_API_KEY` | AI 参加者の早押し判定（[Jev](jev-poc.md)）。未設定なら AI を参加させられない |
| `AI_READING_ENDED_DELAY_MS` | 読み切り後、AI が回答に踏み切るまでの待ち時間（ミリ秒、既定 5000）。0 なら読み切りと同時 |
| `ANTHROPIC_API_KEY` / `GEMINI_API_KEY` / `XAI_API_KEY` | AI 参加者の回答（3 モデルの合議）。未設定なら早押しはするが回答できない |

```bash
QUIZ_CHAR_INTERVAL_MS=300 uv run uvicorn app.main:app --port 8000
```

音声なし問題については[出題データ](quiz-data.md#音声なしで出題する)を参照。
LLM 予測に関する環境変数は [LLM 予測](llm.md)にある。

## 参加者のスマホから繋がらないとき

出題者画面は `localhost` で開けても、参加者のスマホから繋がらないことがある。
上から順に確認する。

### 1. `--host 0.0.0.0` を付けているか

```
Uvicorn running on http://127.0.0.1:8000   ← ループバックのみ。スマホから届かない
Uvicorn running on http://0.0.0.0:8000     ← 正しい
```

省略すると `127.0.0.1` に bind され、**同じ端末からしか繋がらない**。
起動ログの 1 行で見分けられる。

### 2. Mac 自身から LAN IP で開けるか

```bash
curl -s -o /dev/null -w "%{http_code}\n" http://<LAN IP>:8000/player
```

`200` なら、サーバとファイアウォールは問題ない。`000` なら 1. を疑う。

### 3. ネットワークがクライアント間通信を遮断していないか

**ホテル・カフェ・商業施設の WiFi は、端末どうしの通信を遮断していることが多い。**
AP アイソレーション、クライアント分離、プライバシーセパレータなどと呼ばれる。
宿泊客の端末が互いに見えないようにするためのもので、セキュリティ上は正しい設定である。

同じサブネットに居ても、インターネット方向にしか通信できない。
ARP テーブルに他の端末が見えていても、**通信できる保証にはならない**（L2 の情報のため）。

スマホから `http://<ゲートウェイの IP>` を開いてみると切り分けやすい。

回避策:

- **スマホのテザリングを親にする。** 出題者の Mac も参加者もテザリングに繋ぐ。
  ホテルの WiFi を経由しないので分離の影響を受けない。少人数ならこれが最も確実
- **モバイルルーターを持ち込む。** 本番の開催ならこちらが安定する

## 開発時

バックエンドとフロントを別々に動かす。
Vite の dev server が `/api` `/ws` `/quiz_data` `/sound` をバックエンドへ中継するので、ブラウザからは同一オリジンに見える。

```bash
# 1 つ目のターミナル
cd server && uv run uvicorn app.main:app --port 8000 --reload

# 2 つ目のターミナル
npm run dev -w web
```

出題者用は `http://localhost:5173/host.html?token=...`、回答者用は `http://localhost:5173/player.html` で開く。

## テスト

```bash
cd server && uv run pytest
```

早押しの「最初の一人」判定や、古いラウンドの排除は複数端末での同時押しを手動で再現できないため、単体テストが唯一現実的な検証手段になる。

出題者フロント側（AI の判定と合議の非同期制御）は Vitest で見る。

```bash
npm test -w web
```

応答の到着順に依存する挙動（早期確定、遅れて届いたモデルの反映、
ラウンドが変わった後の応答を捨てる）は、型でもブラウザ操作でも落ちない。

## 操作の流れ

1. 出題者が「出題する」を押す。ジングルが鳴り、続いて問題音声が流れる
2. 問題文は読み上げに合わせて投影画面に表示される（回答者の画面には出ない）
3. 誰かが早押しすると、**サーバが最初の一人を決める**。音声と文字送りが止まり、その人の名前が投影される。押した本人の画面には「回答権」が出る
4. 回答を聞いたら出題者が「チェック」を押す。**ここで初めて正解が投影に出る**
5. 「正解」「不正解」を押して判定する
6. 「次の問題へ」で次へ進む

読み切っても自動では締め切らない。
「読み切りました（まだ押せます）」の状態が続き、出題者が「タイムアップ」を押して初めて締め切られる。
読み切ってから数秒は押させるのが通例のため。誰も押さなければ、そこで正解を出してスルーする。

**正解を投影に出すのは「チェック」「タイムアップ」を押した後だけ。**
投影画面は参加者も見るので、回答権を得た時点で正解が見えていると、それを読んで答えられてしまう。
表示するかどうかをフロントに委ねず、サーバが送る phase を絞ることで担保している。

押し間違いは「解除して続ける」で取り消せる。
判定を経ていないので、その人はお手つきにならず、また押せる。
不正解と判定した場合はその問題は終わりで、同じ問題で 2 人目の早押しを受け付ける運用（ダブルチャンス）は行わない。
**AI が誤答した場合も同じ**で、他の参加者へ権利は移らない。

## AI 参加者

出題者画面の「AI 参加者」で参加させると、読み上げ中に [Jev](jev-poc.md) が自動で早押しする。
押したら 3 モデル（Claude / Gemini / Grok）へ並列に投げ、合議で答えを 1 つ決める。

判定と合議の中身は [jev-poc](jev-poc.md) と同じものを使っている。
このドキュメントでは、オンライン版で違う部分だけを書く。

### AI は通常の参加者として扱う

`join_ai` で **Player として登録**し、早押しの排他・お手つき・投影の一覧に人間と同じように乗せる。
AI 専用の経路を作ると、早押しの排他（`room.py` の `buzz()`）を二重に実装することになる。
区別するのは `PlayerView.is_ai` だけで、投影の表示と回答の紐付けに使う。

人間が先に押せば AI は押せず、AI が先に押せば人間は押せない。どちらも `too_late` で弾かれる。

### Jev の判定は出題者フロントで行う

**サーバは文字位置を持たない。** 文字送りは出題者フロントが `.lab` から計算しており、
`room.py` は「早押しを受け付けてよいか」「正解を出してよいか」を決めるためだけに存在する。

そのため Jev の判定も 3 モデルへの送信も出題者フロントで行い、サーバへは結果だけを送る。

| メッセージ | 内容 |
| --- | --- |
| `ai_join` | AI を参加者として登録する |
| `ai_buzz` | AI が早押しする。判定は `Room.buzz` に委ねる |
| `ai_answer` | 合議の結果を預ける。**phase は変えない** |

### LLM へ渡すのは「受理されて止まった位置まで」

3 モデルへ送るのは、`ai_buzz` が受理され（`buzz_accepted`）、読み上げを止めた位置までの問題文である。
投影に出ている問題文と同じになる。Jev が判定に使った文ではない。

判定から受理までの間も読み上げは進んでおり、投影にはその分まで出ている。人間が同じ位置で押した場合にも
同じ範囲が聞こえているため、AI にだけ狭い範囲を渡すと対決の条件が不利になる（[jev-poc](jev-poc.md#渡すのは読み上げられた部分まで) と同じ扱い）。
受理を待ってから送るので、人間が先に押して `too_late` で弾かれた場合は LLM を呼ばない。

`ai_buzz` を `buzz` と分けているのは、`buzz` が「その接続自身の `player_id`」で押すメッセージであるため。
`buzz` へ `player_id` を載せられるようにすると、出題者が任意の参加者になりすまして押せてしまう。

いずれも出題者だけが送れる。回答者から送ると `forbidden` で弾く。

### AI の回答は正解より早く出す

AI が押した直後（`buzzed`）から投影に出る。正解（`check` 以降）より早い。

正解と同じ扱いにする理由が無い。AI の回答は「AI が何と答えたか」であって正解ではなく、
しかも AI が押した時点でそのラウンドの解答権は確定している（ダブルチャンスは無い）。
投影を見ている参加者がそれを読んでも得をする余地が無い。

露出制御は正解とは別の定数（`AI_ANSWER_VISIBLE_PHASES`）で持つ。
同じ定数を使い回すと、片方を広げたときにもう片方まで広がる。

```
buzzed  AI の回答が出る（正解はまだ出ない）
check   正解が出る
```

合議が固まるまでは「考え中…」、早期確定で待っているモデルは「応答待ち…」と出す。
タイムアウトは「応答なし」。待てば来るものと来ないものを区別している。

採用回答は問題文と同じ大きさで出す。投影を会場から読めるようにするため。

各モデルの行の下には、そのモデルが予測した問題文を出す（見せ方は [jev-poc](jev-poc.md#予測した問題文を出す) と同じ）。
予測文も回答と同じく `buzzed` から出す。解答権は確定しているので、ヒントになっても得をしない。
読み上げ済みの部分を見分けるには LLM へ実際に送った文字列が要るため、出題者フロントが
`ai_answer` の `read_text` に載せて送る。押した後の表示文字数から復元すると、送った文字列と一致する保証が無い。
`continuation` / `read_text` は省略可能で、送らない古い出題者フロントからの `ai_answer` も受け付ける。

### 判定は出題者が押す

AI の回答は文字で得られるので自動判定もできるが、採らない。
`judge` は出題者だけが呼べる操作であり、そこへ自動確定の経路を足すと「誰が判定したか」が 2 通りになる。

正解と AI の回答が並んで出ているので、出題者は見て押すだけで済む。

### 判定値の見かた

出題者画面に、Jev の観測値がバーで出る。

| 指標 | 意味 |
| --- | --- |
| `buzz` | 押してよいか。目盛り（0.70）を超えると押す |
| `asking` | 問いの本体に入っているか。30 字以下ではこれも 0.60 以上が要る |
| `parallel` | パラレル問題か。**押下判定には使わない**（記録用）ため目盛りを出さない |

`parallel` を使わない理由は [jev-poc](jev-poc.md#なぜこの形なのか) を参照。

### 読み切り後の待ち時間

読み切っても早押しは締め切られない（締め切るのは出題者の「タイムアップ」）。
人間はこの間も押せるので、**AI も押せないと対決として不公平になる**。

ただし即座には押させない。読み切りの直後は人間が考えている時間であり、
そこへ AI が割り込むと考える間が無くなる。

既定で 5 秒待つ。`AI_READING_ENDED_DELAY_MS` で変えられる（0 なら読み切りと同時）。

```bash
AI_READING_ENDED_DELAY_MS=0 uv run uvicorn app.main:app --host 0.0.0.0 --port 8000
```

この間に人間が押せば AI は押せない（`too_late`）。逆も同じ。

### AI が使えない場合

`TYPESAFE_API_KEY` が未設定なら参加トグルが押せない。オンライン版の他の機能は動く。

各社の API キーが未設定の場合、**早押しはするが回答できない**。
送信せずその場で「回答なし」を返すため、出題が止まることはない。

## 出題の抽選

**全問を 1 つの山としてシャッフルし、頭から配る。** 一巡するまで同じ問題は出ない。

単純な乱数選択では、未出題の問題が残っていても既出が繰り返し選ばれてしまう。
問題数が数十問の規模では体感でわかるほど頻繁に起きるため、山を作って順に消化する方式にしている。

- 山は**サーバプロセスの起動時**に組む。サーバを再起動すると履歴はリセットされる
- 会ごとにサーバを立て直す運用なので、ファイルや DB への**永続化はしない**
- 一度出した問題は、**誤答でもスルーでも**山へ戻さない。会場で読み上げられた時点で消費されている
- 山を使い切ったら組み直す。このとき先頭が直前の問題と重なった場合だけ、先頭と 2 番目を入れ替える。「一巡したのに同じ問題が 2 回続いた」という見え方を避けるため
- 問題を指定して出題した場合も、その問題は山から取り除く

残りの問題数は出題者画面の右下に「残り N / M」として出る。投影の邪魔にならないよう控えめに表示している。

`batch`（`20260820` など）は VOICEPEAK での出力単位でしかなく、難易度やジャンルの意味を持たないため、
バッチをまたいでシャッフルしている。

## 仕組み

| 項目 | 方式 |
| --- | --- |
| 早押し判定 | サーバがメッセージを受け取った順。端末の時計は使わない |
| 出題の抽選 | 全問を 1 つの山にしてシャッフルし、一巡するまで再出題しない（[詳細](#出題の抽選)） |
| 正解の秘匿 | 出してよい phase 以外はサーバが送らない（投影は参加者も見るため） |
| 排他 | asyncio の単一イベントループの直列性に任せる（ロックなし） |
| 古い押し込みの排除 | `round_id` が現在のラウンドと一致しない `buzz` は捨てる |
| 状態の同期 | 差分ではなく状態全体を配る。再接続は繋ぎ直すだけで復元される |
| 文字送り | 出題者フロントが `.lab` から計算する。サーバは介在しない |
| 参加者の同一性 | サーバ発行の token を `localStorage` に持つ。リロードしても復帰する |
| AI の早押し | 出題者フロントが Jev で判定し `ai_buzz` を送る。判定は `Room.buzz` に委ねる |
| AI の回答 | 出題者フロントが 3 モデルへ投げて合議し、結果だけをサーバへ預ける |
| AI の回答の秘匿 | 正解とは別の phase 集合で制御する（押した直後から出す） |

## ファイル構成

```
server/
├── app/
│   ├── main.py       FastAPI アプリ・静的配信・LAN IP の解決
│   ├── quiz.py       questions.csv の読み込みと検証・出題の抽選
│   ├── protocol.py   WebSocket メッセージの定義（web/src/protocol.ts と対）
│   ├── room.py       ルーム状態機械。早押し判定の本体
│   └── ws.py         WebSocket エンドポイント・権限の検証
└── tests/

web/
├── host.html / player.html     2 エントリ構成
└── src/
    ├── protocol.ts             server/app/protocol.py と対にする型
    ├── lib/
    │   ├── lab.ts / align.ts   PoC からコピー（音声と問題文の同期）
    │   ├── sound.ts            ジングル SE
    │   ├── useConnection.ts    WebSocket 接続と再接続
    │   ├── useWakeLock.ts      スマホの画面ロック防止
    │   ├── jev.ts              Jev 判定 API の呼び出し（jev-poc からの移植）
    │   ├── llm.ts              予測 API の呼び出し（jev-poc からの移植）
    │   ├── decision.ts         押下判定（jev-poc・server と同じ規則）
    │   ├── consensus.ts        3 モデルの応答から答えを 1 つ決める
    │   ├── continuation.ts     予測文を読み上げ済み部分と予測部分に分ける（jev-poc と同じ）
    │   └── normalize.ts        合議で回答を比べるための正規化
    ├── host/                   出題者用（投影）
    │   ├── useAiPlayer.ts      Jev 判定と合議の実行、AI としての早押し
    │   ├── AiPanel.tsx         AI の参加操作と判定値のバー表示
    │   └── AiAnswerView.tsx    AI の回答と各モデルの応答・予測した問題文
    └── player/                 回答者用（押しボタン）
```

`lib/` の `jev.ts` `llm.ts` `decision.ts` `consensus.ts` は [jev-poc](jev-poc.md) からの移植で、
**両方に同じものがある**。片方だけ直すと、計測スクリプトで測った成績と実機の挙動がズレる。
`decision.ts` は `server/app/jev/decision.py` とも対になっている。閾値に触るときは 3 箇所すべてを見る。
